Clarification answers and simulator references do not always align with evaluation semantics

Hi organizers,

Could you clarify the intended consistency between the simulated user's privileged reference, its clarification answers, and evaluation? We found two different situations in the released training data: an observed clarification answer conflicts with evaluation, and some privileged references leave evaluator-required behavior unspecified.

A. Observed answer/test conflict: HumanEval/42

The [original `incr_list` prompt](https://github.com/serval-uni-lu/clarification-competition/blob/be108fb8ef4b87ede7b9f8edd1bd3c2166169e29/data/humaneval/humaneval_original.jsonl#L43) asks to increment list elements by 1, without an integer-only element restriction. Our captured interaction was:

> **Question:** Should incr_list raise an error, ignore, or handle differently when the input list contains non-integer elements or invalid types?
>
> **Recorded score:** `QUALITY=3`, requirement ID `non-integer-handling`
>
> **Answer:** The function should raise a TypeError if any element in the input list is not an integer.

The resulting implementation followed the answer:

def incr_list(l: list):
    if not all(isinstance(x, int) for x in l):
        raise TypeError("All elements must be integers")
    return [x + 1 for x in l]

However, the EvalPlus inputs used by evaluation include `[2.5, 3.7, 8.9, 1.2, 0.5]`, for which the reference expects `[3.5, 4.7, 9.9, 2.2, 1.5]`. The answer-following code raises `TypeError` instead, as recorded in our evaluation result.

We replayed the captured code with the current local Docker evaluator: it fails, while removing only the two-line integer guard makes it pass all 3 base and 999 plus inputs. This isolates the restriction introduced by the answer as the cause of this failure.

`QUALITY=3` here is the simulator's recorded score, not an independent certification. This is a replay of a saved interaction; it does not claim that sampling the model again always yields the same answer.

B. Reference coverage: MBPP/753

In [`_build_human_system_prompt`](https://github.com/serval-uni-lu/clarification-competition/blob/be108fb8ef4b87ede7b9f8edd1bd3c2166169e29/clarify/env.py#L156-L172), the simulator receives `clarifications` when available, otherwise `reference_prompt`. The [MBPP/753 variant](https://github.com/serval-uni-lu/clarification-competition/blob/be108fb8ef4b87ede7b9f8edd1bd3c2166169e29/data/mbpp/mbpp_larbi_contradictory.jsonl#L753) has no matching clarification overlay, and its decoded reference is:

Write a function to find minimum k records from tuple list.
assert min_k([('Manjeet',10), ('Akshat',4), ('Akash',2), ('Nikhil',8)], 2) == [('Akash',2), ('Akshat',4)]

Both ordinary tuple ordering and ordering by the second numeric field satisfy this reference example. They also agree on the second checked-in assertion. In the third assertion, the two policies select `('Amer',11)` and `('Ayesha',9)` respectively; evaluation requires the latter. The reference does not identify the comparison field.

Similarly, [MBPP/627](https://github.com/serval-uni-lu/clarification-competition/blob/be108fb8ef4b87ede7b9f8edd1bd3c2166169e29/data/mbpp/mbpp_larbi_contradictory.jsonl#L627) gives `[0,1,2,3] → 4`, which does not distinguish a missing-number domain starting at 0 from one starting at 1, while evaluation distinguishes them.

These are reference-coverage observations, not observed simulator failures. A model may infer the intended convention. We are not claiming that insufficient reference information caused the particular answer in case A.

Requested clarification

1. Are simulated-user answers intended to be authoritative? When following an accepted clarification answer conflicts with evaluation, how should participants handle and report the case, and how is it treated in scoring or regrading?
2. Is simulator fallibility an intended part of the task? If so, what behavior is expected without evaluation-test access and under the default one-turn clarification budget?
3. Does official evaluation provide additional authoritative context, or validate that simulator-only references contain the behavioral choices required by evaluation? Could reference coverage and answer consistency be checked separately, with a process for correcting or flagging affected samples?

The coding assistant can continue to receive the same public interface and have no access to evaluation tests. The concern is whether the clarification channel supplies intended behavior consistent with evaluation.

Verification context

- Repository baseline: `be108fb8ef4b87ede7b9f8edd1bd3c2166169e29`.
- Case A: agent and simulator configured as `openai/gpt-4.1-mini`; `evalplus==0.3.1`; HumanEvalPlus hash `fe585eb4df8c88d844eeb463ea4d0302`.
- The local replay includes an entry-point compatibility fix; both sides use `incr_list` here, so that fix does not affect the demonstrated conflict.
- Case B is reproducible from the released JSONL by decoding `REF_` with base64 and zlib and comparing the two sorting policies; it requires no model calls.
