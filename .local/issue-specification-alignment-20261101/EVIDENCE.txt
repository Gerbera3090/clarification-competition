Strong examples
===============
Mbpp/753, data/mbpp/mbpp_larbi_contradictory.jsonl:753:
Decoded reference gives one example. Both normal Python tuple ordering and
ordering by the numeric second field produce exactly that example's expected
output. Both also pass the second checked-in assertion. For the third assertion,
normal tuple order selects ('Amer', 11), while the expected result is
('Ayesha', 9), consistent with ordering by the numeric second field.
The reference does not explicitly identify which tuple field defines minimum.
This is the stronger example of a residual specification choice.

Mbpp/627, same file:627:
The decoded reference has [0,1,2,3] -> 4. Searching for the first missing
nonnegative integer and searching for the first missing positive integer both
produce 4. Both also match the second checked-in assertion. For [2,3,5,8,9],
the former gives 0 and the latter 1; the checked-in assertion expects 0.
Caveat: a simulator could reasonably infer nonnegative semantics from the
zero-containing example or known problem convention. This example establishes
that the example does not distinguish the domains, not that no inference is
possible. The arguments (array, 0, end) may themselves provide a convention cue.

Mbpp/461, same file:461 (separate issue/category):
The decoded reference says to count uppercase characters, but its own example
upper_ctr('PYthon') == 1 disagrees with the conventional uppercase count 2.
The checked-in tests also expect upper_ctr('BigData') == 1 (conventional count 2).
This is source/example inconsistency, not simply a missing simulator fact.
Giving all tests to the simulator would not itself explain the intended rule.
